# ATW Agent 单命令交接与进度通知改造方案

审查基线为 `89802e5`。本方案已落实到 ATW 1.1.0 工作区。实际命令、使用示例和验收记录见 [Agent 交接和进度](agent-progress.md)。

## 1. 交付目标

1. Agent 在计算节点执行一条命令，接管已启动的本次任务，得到可程序化校验的回执。成功回执给出 `request_id`、`task_id`、`revision`、`monitoring` 和绑定进程身份。
2. 使用现有训练 CSV 的单项任务无需修改训练脚本。串行和并行队列通过同一套清单汇总，支持等权和非等权，并分别显示执行比例和验收比例。
3. Agent 退出后，ATW 持续只读采样并发送定时钉钉消息。计算程序及原有成功、失败和告警规则仍由现有执行和监控流程处理。
4. 新服务继续受理原 AFHP/1 请求。升级和回退保留现有监控状态、回执和待发通知，并在 Windows、Linux 环境分别实测。

## 2. Agent 操作方式

普通训练任务的命令样例，路径和成功标记需换成本次运行的真实配置：

```bash
atw handoff --task-id yolo-s07 --request-id req-yolo-s07-01 \
  --name 'UAV-YOLO S07' --pid 12345 --run-dir /runs/s07 \
  --log /runs/s07/train.log --result /runs/s07/best.pt \
  --success-log '<实际训练完成标记>' \
  --progress-csv /runs/s07/results.csv --progress-column epoch \
  --counter-base 1 --total 200 --unit epoch \
  --request-out /runs/s07/atw-request.json --wait 30 --json
```

- `atw handoff` 运行在 ATW 服务所在节点，沿用服务的 `--home`、`--config` 和账户权限。Agent 在 SSH 前先选定本次任务 ID 和请求 ID，断线后可直接查询原请求。命令在节点上取得 PID 创建时间，已有确定的身份时也可传入 `--create-time` 作为预期值。原因明确且可唯一定位时支持现有 `match` 方式。
- `--dry-run` 解析路径、验证进程与配置、读取可用的进度样本，输出拟投递内容及诊断。实际投递时，`--request-out` 优先保存本次准备好的请求，供中断后重放。再次执行 `handoff` 时，如该文件对应相同任务和请求，复用其中的请求，参数与文件不符时报告冲突；改变配置应使用新的请求或 `update`。
- `atw submit FILE --wait 30 --json` 受理自定义 AFHP JSON，包括已有脚本生成的请求和带 revision 的配置更新。两个入口共用请求校验、原子投递和回执等待。`atw receipt ID` 始终可按原 ID 查询。保留直接投递 AFHP inbox 的现有方式。
- 既有任务复用实际日志和结果路径。Agent 能从启动命令、运行配置或调度记录确认时直接使用。只有路径、成功判据或进程身份等必要信息无法确定时才提问。进度来源必须显式选择 `--progress-csv`、`--progress-plan` 或 `--progress-unknown '原因'`。`--progress-unknown` 走原协议，并在接入结果中记录原因。
- 可信的实际启动时间优先通过 `--run-started-at` 提供。专用训练或队列根进程可以用其创建时间作为默认值，CLI 应标明时间来源。长驻调度器的启动时间不能代表本次运行，需提供本次任务启动时间并绑定能代表该批任务寿命的队列根进程。修复旧生成器在已有任务场景下把当前时间当作启动时间的行为。
- 接入成功要求退出码为 `0`，原回执匹配本次请求、任务、revision 和目标身份，并且 `status=accepted`、`monitoring=true`。明确拒绝返回 `1`，回执等待超时返回 `2` 并给出原请求 ID。超时可继续查询或通过 `submit` 重放保存的原请求。确认请求确实过期且任务未受理后，才生成新请求 ID，保留同一个实际运行的任务 ID。

### 投递与幂等

`submit` 在服务配置指定的 inbox 文件系统中创建完整临时文件，关闭并同步后以原子且不覆盖的方式发布。Windows 和 Linux 验证所在文件系统的发布能力，无法安全发布时给出明确错误。当前 `atomic_write_bytes` 使用 `os.replace`，适用于允许替换的文件，inbox 需要独立的防覆盖发布操作。同一 ID 的待消费文件按规范化请求哈希判断重复或冲突，SQLite 事务中的原请求行是最终权威。

必须同时修复直接投递旧路径的冲突处理。当前 `handle_raw` 可拒绝同 ID 的不同内容，但 `process_file` 仍调用 `_publish`，后者会按同 ID 写拒绝回执。修复时将冲突文件与原请求分别归档，原 ID 的标准回执始终来自首次落库结果。新 CLI 在接到回执后用本次请求哈希核对权威请求行，避免并发时误读另一提交者的受理结果。保留原有回执格式，冲突由本次 CLI 返回并在服务诊断中可查。 [当前请求处理](../src/atw/tasks/service.py#L96) · [回执发布](../src/atw/tasks/service.py#L686) · [现有冲突测试](../tests/integration/test_intake.py#L75)

## 3. 进度协议和计算

### 协议与存储

- AFHP/1 基线已冻结，旧版对未知字段严格校验。发布新增 `atw.task.v1.1` 请求 schema，复用现有任务、规则和版本控制字段，新增可选顶层 `progress`。仍使用 `atw.receipt.v1`。新服务根据协议版本路由到相应校验器，生成并检查两份请求 schema。基本交接继续生成 `atw.task.v1`。 [协议基线](protocol.md#4-register-request) · [请求模型](../src/atw/models/task.py#L290)
- `progress` 取 `csv` 或 `queue`。单项配置直接描述 CSV 路径、列、计数起点、总量和单位。队列 CLI 从 `--progress-plan` 读取静态清单，把规范化配置放入请求，清单之后的编辑通过 `update` 生效。`changes.progress` 缺省为沿用，显式 `null` 为移除，对象为整项替换。更新沿用 `expected_revision`，切换数据源时清空旧采样缓存。
- 将进度配置与最新样本放在现有 `runtime_json` 的独立版本化对象中，两者分字段保存。[现有模型](../src/atw/storage/records.py#L24) 按严格模型反序列化 `evidence_json`，因此上一轮草案里的 `evidence.progress` 会让旧服务读到新版数据时面临反序列化失败。配置和采样沿用现有任务事务，并在任务版本快照和 `show --json` 中显式展示。回退可用性须用旧程序实际开新版数据库验证。
- 运行中的服务会话发布自己的协议能力，CLI 依据同一 `ATW_HOME` 下的有效会话判断支持情况。两端版本不匹配时，要在提交前提示升级。直接向旧服务投递新版请求由原有 `UNSUPPORTED_PROTOCOL` 路径处理。 [会话登记实现](../src/atw/service/runner.py#L92)

### 单项 CSV

读取本次运行专属 CSV 的最后一条完整数据行。列值为整数时，`counter_base=1` 表示值已是完成量，`counter_base=0` 表示首个已完成单位对应值 0，计算时加 1。缺表头、未写完的首行、计数越界或来源失效时给出可诊断的采样状态。追加中的尾行可暂时沿用前一条完整记录。每轮读取受字节和行长限制，达到限制时报告原因并继续监控。关联本次运行的路径和时间需在预检时核对，CSV 文件更新只证明计数发生变化。

### 串行和并行队列

| 数据 | 写入方与含义 |
|---|---|
| 静态清单 | Agent 从本次队列定义生成。包含本次 `task_id`、每个 `item_id`、`total`、`unit`、`weight`、是否必做及其数据源。ID 唯一，`total` 和权重为有限正值。默认等权，长短任务差异大时允许按同一工作量单位配置权重。 |
| 子任务状态文件 | 队列控制器或该子任务的唯一写入者负责。包含 `task_id`、`item_id`、`attempt`、`state`、`completed`、`updated_at`、可选 `acceptance`。使用 `atw progress report` 生成并原子写入。配置了 CSV 的项可以省略 `completed`，由读取端从 CSV 取得。 |
| 可选 CSV 计数 | 已输出 CSV 的子任务可声明 `csv` 计数来源。队列只需报告状态、attempt 和验收结果，ATW 从 CSV 读取轮数。重试使用本次 attempt 独立的 CSV 文件，由清单声明可解析到运行目录内的路径。 |
| 验收状态 | 由项目自己的结果校验逻辑明确报告 `accepted`、`rejected` 或 `pending`。没有该信息时显示验收未知或省略验收行。 |

队列命令用 `--progress-plan /runs/screening/progress-plan.json` 替换单项 CSV 选项，绑定队列主进程。下面是一个使用状态文件的两项队列清单。CLI 将相对状态路径解析到本次运行目录中，再放入请求。

```json
{
  "schema": "atw.progress.plan.v1",
  "task_id": "yolo-screening",
  "items": [
    {"id": "S07", "total": 200, "unit": "epoch", "weight": 3, "required": true,
     "report": "progress/S07.json"},
    {"id": "S08", "total": 100, "unit": "epoch", "weight": 1, "required": false,
     "report": "progress/S08.json"}
  ]
}
```

项目可在入队时批量生成初始 `queued` 状态。接入已经运行的队列时，依据当前队列状态补录。定制脚本在阶段推进时可调用：

```bash
atw progress report --plan /runs/screening/progress-plan.json \
  --item S07 --attempt 1 --state running --completed 62
```

- 每项只有一份权重，多个 GPU 或 worker 协作仍使用同一子任务 ID。`progress report` 仅读写该项进度文件，使用跨进程锁包住读取、检查 attempt 和原子替换。同一 attempt 的计数单调，状态按 `queued → running → completed / failed` 推进，直接提交有真实依据的完成状态也可用于补录。验收在执行完成后更新。重试由控制器提交更高 attempt，同时重置该项执行和验收状态。晚到的旧 attempt 更新直接拒绝。同一项的重试沿用 ID 和权重，并以当前 attempt 重新计算，整批比例因此可以回落。ATW 读端也校验标识、attempt 和范围。
- 执行比例为 `100 × Σ(weight × completed / total) / Σ(weight)`。明确排队的项贡献 0，计算完成的项具有 `completed=total`。失败项可保留已执行的计数，同时显示失败数量。跳过的可选项标为 `skipped`，贡献 0，并显示跳过数量。缺数据的项仍计入计划分母，对整批输出 `进度未知`，或者显示同一清单的最近完整快照和时间。已发现切换 attempt 的项禁止用上一 attempt 冒充当前值。队列减少或增加条目时通过 revision 更新分母。
- 验收比例为验收通过项数除以计划项数，同时显示必做项的通过数和总数。排队、运行、失败、执行完和验收通过各有明确口径。100% 执行进度仍由现有终态规则对任务单独判定。百分比在渲染时取一位小数，未达到 100% 时避免舍入成 100%。

计算样例：10 项等权，7 项完成且验收通过，另一项 62/200，剩余两项明确排队，执行进度为 73.1%，验收进度为 70%。若一个权重为 3 的任务完成 50%，另一个权重为 1 的任务完成 100%，整批执行进度为 62.5%。两个样例都应成为自动化验收用例。

### 数据读取和恢复

- 所有读取源在预检、受理和运行期都受 `allowed_read_roots` 与本次运行目录限制。只读有界的普通文件，拒绝路径穿越、目录、链接越界和特殊设备。文件开始前尚未创建属于可报告的来源状态。CLI 和服务不得借进度接入改变运行目录或已有文件权限。现有原子写入工具会对父目录调用 `secure_mkdir`，项目目录写入需复用无父目录权限副作用的底层操作。 [路径校验](../src/atw/utils/pathsafe.py#L39) · [原子写入](../src/atw/utils/atomic.py#L13)
- 进度读取沿用监督采样，保留旧定时推送频率。采样异常写入单项诊断，进程采样与现有规则继续执行。实现时使用固定的每源读取和队列项数上限，并测试大队列的采样开销。初始建议上限为每队列 256 项、请求沿用配置体积上限、状态文件每项 16 KiB、CSV 每源 8 MiB。完整 CSV 按变更读取，多个源同轮触发时也要控制总读取量。超过上限的项给出原因。
- 持久化最近一次有效计数、采样时间、数据来源时间和单项诊断，缓存与进度配置、item 和 attempt 对应，只在进度配置实际变更时清空。暂时读不到时标注快照时间。已完成或明确排队的项无需周期性续写。运行项只在显式配置过期阈值或来源不可读时标为快照，长 epoch 时保留计数与采样时间。服务重启后先校验进程和数据源归属，再继续采样。 [当前采样流程](../src/atw/monitoring/supervisor.py#L92)

## 4. 通知形态

> **[ATW] UAV-YOLO 200 轮初筛 · 执行 73.1%**<br>
> 已验收 7/10 · 必做 7/7 · 排队 2<br>
> S07 · 62/200 轮 · C2 · 已运行 10 小时 20 分

以上为上一节假设下的样式样稿。用户原消息可确认的是验收 7/10、必做 7/7 及 S07 的 62/200 快照。正式通知按有证据的口径显示。多项同时运行时最多显示两项，再显示其余在跑数量。单项任务标题显示 `31%`，单行显示 `62/200 轮`。只有验收数据时标题显示 `已验收 70%`。旧任务默认显示任务名、监控状态、节点和耗时。

`show --json` 返回执行进度、验收计数、来源状态、快照时间和各项计数，并保留原有键。任务编号、revision、CPU、分卡显存和其他诊断走详情。相关资源告警直接写出触发指标。定时通知沿用已有间隔及 outbox，首期只改进度消息模板和必要的告警信息。 [当前进度事件](../src/atw/monitoring/supervisor.py#L400) · [当前模板](../src/atw/notifications/templates.py#L157)

## 5. 合理性审查与处理方案

在 Windows 临时 ATW 目录中曾复现回执问题：首个请求受理，同 ID 的不同内容返回 `REQUEST_CONFLICT`，落盘回执变为 `rejected`，SQLite 中原请求保持 `accepted`。基线测试为 122 项通过、2 项跳过。1.1.0 的回归测试现已同时断言标准回执、任务配置和冲突归档。

| 审查发现 | 处理方案 | 通过标准 |
|---|---|---|
| **阻断。** 接入时刻被当作启动时刻，旧日志和已有结果可能被判过期。 | 读取本次运行真实启动时间。专用根进程可用创建时间，长驻调度器必须提供本次运行时间。旧生成器支持显式时间，并删除交接时刻默认值。 | 已启动一段时间的任务可以命中本次早期日志，前一轮的日志或结果仍被拒绝为本轮证据。 |
| **阻断。** 同一请求 ID 的冲突拒绝可覆盖原回执。并发或断线时还可能重建请求，导致原 ID 内容变化。 | CLI 保存原请求并复用哈希，采用不覆盖发布；服务冲突分流，卡住回执写入时可从 SQLite 重建原回执。CLI 等待结果时核对本次请求哈希。 | 两客户端提交同 ID 的相同或不同内容、服务提交后崩溃、SSH 断开后重试。只出现一次受理事件，原回执始终可查询，冲突提交得到明确拒绝。 |
| **阻断。** 将新增字段直接放入 `evidence_json` 会破坏运行中的回退。新 CLI 还可能遇到旧服务进程。 | 单独发布新版请求 schema，服务会话发布能力，运行数据使用已有 JSON 容器。切换版本前确认新版 inbox 请求已处理，未处理的记录逐项保全。 | 旧请求由新服务正常受理。新任务接入后，使用基线版本对生产形状的 SQLite 副本启动、采样、查询并完成旧格式更新，后续再升版能恢复进度。 |
| **高。** 进程数随 worker、数据加载器和 GPU 数量变化，不能作为队列比例。 | 分母和权重来自清单，状态与计数按 item ID 聚合。已存在 CSV 的队列只需补状态和验收来源。 | 串行、并行、两 worker 协作同一项时，同行计数和权重相同；等权 73.1% 和非等权 62.5% 均可复现。 |
| **高。** 并发读写、重试和旧文件可能让进度倒灌。 | 每项独立文件、唯一写入者、原子替换、attempt 校验和本次运行专属路径。快照按配置和 attempt 隔离，允许有来源的重试回落。 | 多项并发写、注入晚到 attempt、截断 CSV、同名旧文件、短暂不可读和 ATW 重启，结果均符合状态定义。 |
| **高。** 自动识别工具若猜测成功标记，可能制造错误验收。 | `handoff` 使用项目明确给出的成功规则，复杂规则通过 `submit` 原样提交，验收计数取项目验证状态。 | 进度为 100%、文件存在但验收规则不成立时，ATW 保持原判定逻辑。 |
| **中。** 自定义 `ATW_HOME`、Windows 文件名、跨用户权限、路径边界和文件体积会影响便捷入口。 | 复用 ATW 路径解析和权限校验，CLI 生成跨平台安全 ID。已有原始请求 ID 语法按旧协议解析，无法作为本机文件名的值在 CLI 发布前报错。验证 Windows 大小写碰撞和路径权限。 | 使用自定义目录、空格与中文路径、越界链接和超大输入测试。合法输入可用，非法输入报告原因，计算进程和项目目录权限保持正常。 |

结论：CLI、进度来源和通知模板的分工合理，现有 inbox、规则、数据库与 outbox 可承接改造。单命令可以降低交接成本，CSV 和每项状态文件可以覆盖当前训练与队列场景。启动时间、回执权威与回退三项需要通过实测，才能作为上线能力交付。

| A. 交接闭环 | `cli/app.py` 的新命令、共享投递逻辑、`tasks/service.py` 的回执冲突修复、Skill 生成器的启动时间修复。 | `validate`、`receipt` 和原 inbox 继续工作。真实服务中运行一条 `handoff` 命令得到正确回执，并验证断连、超时、幂等和冲突。 |
| B. 进度闭环 | `models/task.py`、schema 导出、任务运行状态、监督采样、`progress report` 和 `show --json`。交付两类可运行示例和协议文档。 | 一项任务的 62/200→63/200 由 ATW 自动采样；串行、并行、非等权、失败重试、缺数据和重启均有可重复的用例。测试更新 revision、移除进度和旧版回退。 |
| C. 消息与交付 | 钉钉进度模板、repo Skill、README、部署说明和验收记录。发布产物沿用现有 CI。 | Windows、Linux 各完成一次真实本机服务和 mock 通知端到端。对批准的钉钉测试目的地验证实际样式。发布产物与 Skill 同一版本，在目标节点确认运行的服务会话支持进度后，再同步本机安装的 Skill。 |

验收覆盖最小完整链路：启动独立测试进程 → 单命令接入 → 同一 `task_id` 下观察两个有效计数 → 捕获钉钉模板输出 → 原有规则给出终态。队列用另一个带必做/可选项的运行验证并发与验收。自动化测试使用 mock notifier，现场样式用实际钉钉客户端验收，分别记录结果。检查 `pytest`、schema exporter 和 `ruff`，以对应发布构建的测试结果为准。

上线优先选一台测试节点和平行测试任务。按现有升级工具备份数据库和旧版本，检查升级后原任务续采样与 outbox。新版请求启用后若有问题，先停用新进度接入，记录和核对未消费的新版请求，再用已通过数据库回退演练的上一个版本恢复。核对新旧回执及 outbox，计算进程继续由原运行方式管理。 [Linux 升级和回退](deployment-linux.md#5-verified-wheel-upgrade-and-rollback)
